## UC-GROK-01 — I am new and have not put my API key in yet → **PASS**

Step 1, with no credential:

```
$ env -u XAI_API_KEY ./scripts/go.sh run ./cmd/stt-probe -provider grok -seconds 1
provider=grok language=es
[      0s] canceled code=NotConfigured configura la API key de xAI en Ajustes
[      0s] stopped
start failed: configura la API key de xAI en Ajustes
```

Step 2, the same command with a credential present — the result **changes**, so step 1 came from
reading the key and not from always failing the same way:

```
$ XAI_API_KEY=xai-wrong-key-for-uc01 ./scripts/go.sh run ./cmd/stt-probe -provider grok -seconds 1
provider=grok language=es
           STT-ERR  el handshake con xAI falló (status 400) → AuthenticationFailure
[   485ms] canceled code=AuthenticationFailure xAI rechazó la API key — revísala en Ajustes
[   485ms] stopped
```

Verification: ✅ `NotConfigured`, a message that names Settings, and a different result once a
credential is present. The session ends cleanly (`stopped`), it does not hang.

## UC-GROK-02 — I pasted the key wrong → **PASS**

Against the **real** service. A single `canceled`, and the message names the API key instead of
giving a generic "status 400":

```
[   485ms] canceled code=AuthenticationFailure xAI rechazó la API key — revísala en Ajustes
```

**This is what this journey discovered**, and it was not in the docs: xAI rejects an invalid key
with **HTTP 400**, not with the 401 its own error table documents. The body:

```
HTTP/2 400
{"code":"Client specified an invalid argument",
 "error":"Incorrect API key provided. You can obtain an API key from https://console.x.ai."}
```

Without reading that body the user would have seen "xAI rechazó la petición (status 400)" and
would have started auditing their configuration. Fixed in `internal/stt/grok/errors.go`
(`handshakeFailure`), and noted in the research.

Persistence — the emitted code, classified by the **real** retry policy:

```
  NotConfigured          → class=config   reconnect=false
  AuthenticationFailure  → class=auth     reconnect=false
  BadRequest             → class=config   reconnect=false
  ConnectionFailure      → class=network  reconnect=true
  ServiceTimeout         → class=network  reconnect=true
  TooManyRequests        → class=network  reconnect=true
```

Verification: ✅ none of the three codes this provider emits for a bad or absent credential
retries. That is the property that matters: Grok bills **by the hour**.

## UC-GROK-03 — I dictate two sentences and they appear as one message → **BLOCKED**

There is no xAI key. The same blocker as Azure (`CONTINUITY.md`). It is the only journey that can
confirm the design's central property (an assembled timeline, without duplicates) against the real
server, and also the experiment that resolves risk 1 in the plan — whether word times really are
session-relative. **Run as soon as there is a credential.**

What **is** verified without an account, against a real local WebSocket server
(`httptest` + `websocket.Accept`, not a library mock): the frame format (binary PCM,
`audio.done` as text, the exact `Authorization` header, the query params), the assembly of several
finals into one message, the empty `transcript.done` that erases nothing, the timeouts, the abrupt
close, buffer saturation, and that `Stopped` comes out exactly once per exit path. 60 cases in
`internal/stt/grok`, green with `-race`.

## What this phase found (neither the plan nor the two design reviews saw these)

1. **The 400 instead of the 401** — above.
2. **`Stop` was losing the tail of the dictation.** `select` chooses at random among ready cases,
   so the stop could beat its own audio and send `audio.done` before the last frames. The test
   reproduced it: **4 of 80 bytes** were arriving. Fixed by draining before finalising.
3. **The timeline replacement used the convex hull** of the incoming words, so it erased stored
   words that fell inside a silence in the new event. Fixed by comparing against each incoming
   word.
