```
$ env -u XAI_API_KEY ./scripts/go.sh run ./cmd/stt-probe -provider grok -seconds 1
provider=grok language=es
[      0s] canceled code=NotConfigured configura la API key de xAI en Ajustes

Paso 2, la misma orden con una credencial presente — el resultado **cambia**, así que el paso 1

```
$ XAI_API_KEY=xai-wrong-key-for-uc01 ./scripts/go.sh run ./cmd/stt-probe -provider grok -seconds 1

Verificación: ✅ `NotConfigured`, mensaje que nombra Ajustes, y un resultado distinto al tener

## UC-GROK-02 — me equivoqué al pegar la key → **PASA**

Contra el servicio **real**. Un solo `canceled`, y el mensaje nombra la API key en vez de dar un
"status 400" genérico:

```
[   485ms] canceled code=AuthenticationFailure xAI rechazó la API key — revísala en Ajustes
```

**Esto es lo que este recorrido descubrió**, y no salía de los docs: xAI rechaza una key
inválida con **HTTP 400**, no con el 401 que su propia tabla de errores documenta. El cuerpo:

```
HTTP/2 400
{"code":"Client specified an invalid argument",
 "error":"Incorrect API key provided. You can obtain an API key from https://console.x.ai."}
```

Sin leer ese cuerpo el usuario habría visto "xAI rechazó la petición (status 400)" y se habría
puesto a auditar su configuración. Corregido en `internal/stt/grok/errors.go`
(`handshakeFailure`), y anotado en la investigación.

Persistencia — el código emitido, clasificado por la política de reintentos **real**:

```
  NotConfigured          → class=config   reconnect=false
  AuthenticationFailure  → class=auth     reconnect=false
  BadRequest             → class=config   reconnect=false
  ConnectionFailure      → class=network  reconnect=true
  ServiceTimeout         → class=network  reconnect=true
  TooManyRequests        → class=network  reconnect=true
```

Verificación: ✅ ninguno de los tres códigos que este proveedor emite ante una credencial mala o
ausente reintenta. Es la propiedad que importa: Grok factura **por hora**.

## UC-GROK-03 — dicto dos frases y aparecen como un solo mensaje → **BLOQUEADO**

No hay key de xAI. Mismo bloqueo que Azure (`CONTINUITY.md`). Es el único recorrido que puede
confirmar la propiedad central del diseño (una línea de tiempo ensamblada, sin duplicados) contra
el servidor de verdad, y también el experimento que resuelve el riesgo 1 del plan — si los
tiempos de palabra son de verdad relativos a la sesión. **Ejecutar en cuanto haya credencial.**

Lo que **sí** está verificado sin cuenta, contra un servidor WebSocket local real
(`httptest` + `websocket.Accept`, no un mock de la librería): el formato de los frames (PCM
binario, `audio.done` como texto, el header `Authorization` exacto, los query params), el
ensamblado de varios finales en un mensaje, el `transcript.done` vacío que no borra nada, los
timeouts, el cierre abrupto, la saturación del búfer y que `Stopped` sale exactamente una vez por
cada ruta de salida. 60 casos en `internal/stt/grok`, verdes con `-race`.

## Lo que esta fase encontró (no lo vieron ni el plan ni las dos revisiones de diseño)

1. **El 400 en vez del 401** — arriba.
2. **`Stop` perdía la cola del dictado.** `select` elige al azar entre casos listos, así que el
   stop podía ganarle a su propio audio y mandar `audio.done` antes de los últimos frames. El
   test lo reprodujo: llegaban **4 de 80 bytes**. Arreglado drenando antes de finalizar.
3. **El reemplazo de la línea de tiempo usaba la envoltura convexa** de las palabras entrantes,
   así que borraba palabras almacenadas dentro de un silencio del evento nuevo. Arreglado
   comparando contra cada palabra entrante.
